# UI redesign, phase 3: polish, WCAG 2.2 AA and voice — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Both apps (the portal, the reader; the desktop app, where you operate) usable from the keyboard alone, with a
visible focus that nothing covers, targets of 24 px or more, the same loading / empty / error states everywhere, and
copy in the intern shrimp's voice without jargon the user has not met. New screenshots and an animated tour.

**Decisions taken with the user:** "unit" stays (the plan, the wizard, the CLI and the README use it); the desktop
app gets its ⌘K palette and `g` shortcuts (left over from phase 2); the tour GIF is built with Pillow, downloaded into
uv's cache for a throwaway script only (not a kit dependency).

## WCAG 2.2 AA targets (the ones this UI can break)

- 2.1.1 Keyboard, 2.1.2 No keyboard trap: every action reachable with Tab / Enter / Space / Esc; dialogs are native
  `<dialog>` (focus moves in and back).
- 2.4.1 Bypass blocks: a "skip to content" link first in each app.
- 2.4.3 Focus order, 2.4.7 Focus visible, 2.4.11 Focus not obscured (minimum): one focus ring for everything
  interactive, from the shared kit, contrast 3:1; the portal's sticky header keeps `scroll-padding-top`.
- 2.5.8 Target size (minimum): 24 × 24 px for every control (small buttons are 32 px; checkboxes take their label).
- 4.1.2 Name, role, value: the palettes as combobox + listbox with `aria-activedescendant`; toggles with
  `aria-pressed` / `aria-expanded`; landmarks named.
- 1.4.3 / 1.4.11 contrast: the tokens' test already checks 4.5:1 text in both themes; the focus colour is added.

## Tasks (one commit each)

1. **Foundations.** One `:focus-visible` rule for every interactive element in `ui/src/ui.css` (both apps load it),
   its colour checked at 3:1 against both canvases; a skip link and a `main` landmark with an id in each app; nothing
   under 24 px. Tests: `ui/src/style.test.js` (the rule, the sizes), Vitest render checks for the skip links.
2. **Keyboard in the app.** A ⌘K / Ctrl K palette (sections, projects, actions) and `g` shortcuts (`g s` Summary,
   `g p` Plan, `g i` Interviews, `g t` Team, `g q` Quality, `g d` Docs, `g m` Machine, `g k` Kit dev), shown in the
   palette and as hints in the sidebar. Pure helpers (entries, matching, the shortcut map) under Vitest; the palette
   reuses the portal's pattern (combobox, listbox, `aria-activedescendant`).
3. **States and the portal's last fixed strings.** A section that fails says the server's message and offers "Try
   again"; the same skeleton while loading; the portal's Pipeline gets its strings (status labels, drawer, log, run
   line) in `es` and `en`.
4. **Voice.** Every string of both apps read again: short, `tú`, no runner / worktree / drift where a person reads
   it (CI keeps "runner", its own word), at most one joke per screen and only where the user waits or succeeded,
   none in errors, decisions or uninstall.
5. **Screenshots, tour and closing.** New README screenshots and `app-tour.gif` (frames from the real app on the
   bench, assembled with Pillow); the WCAG checklist below walked in both apps; README / tutorial; `VERSIONS["kit"]`.

## Verification per commit

- `npm test` and `npm run build` in `portal/app` and `desktop/renderer`; `node --test "test/*.test.cjs"` in
  `desktop/`; the pytest files of what changed; the full suite before the PR.
- The real app on the bench (CDP): Tab through each section and the portal, check the focused element is visible and
  not under the header; the palettes with the keyboard only.
